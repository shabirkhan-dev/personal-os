This page is the one place the NestJS API contract lives. The agent contract in
`.agents/agent-contract.md` points every role here: web and mobile read it before consuming an
endpoint, and backend updates it in the same commit as any public API change.

Endpoints are listed here as clients start using them. A contract that lives in one file stays
consistent; one scattered across cards and notes drifts immediately.

## What belongs here

- Every public endpoint: method, path, auth requirement, request and response shape.
- The response envelope, error shape and status-code conventions.
- Pagination, filtering and sorting conventions.
- Breaking changes, with a dated changelog entry below.

## What does not

- Implementation detail, internal service structure, database schema.
- Anything still being designed — raise a board card for that instead.

## Endpoints

All paths are under `/api/v1`. Errors use `{ "code": string, "message": string }` with the HTTP
status. Native clients send `X-Client-Platform: native` so session responses include the refresh
token in the body (browsers get an httpOnly cookie instead).

| Method | Path | Auth | Purpose |
| --- | --- | --- | --- |
| `GET` | `/health` | none | Liveness probe |
| — | `/api/docs` | none in dev | Swagger UI |
| `POST` | `/auth/methods/email-code/request` | none | Send a 6-digit sign-in code; creates the account on first use |
| `POST` | `/auth/methods/email-code/verify` | none | Exchange the code for a session |
| `POST` | `/auth/refresh` | refresh token | Rotate the session |
| `POST` | `/auth/logout` | refresh token | End the session |
| `GET` | `/auth/me` | bearer | Current user |
| `GET` | `/users/me` | bearer | Current user with profile |
| `PATCH` | `/users/me/profile` | bearer | Update profile fields |
| `POST` | `/users/me/avatar` | bearer | Upload an avatar image (multipart `file`) |
| `GET` | `/users/me/onboarding` | bearer | Saved onboarding answers, or `null` before the first save |
| `PUT` | `/users/me/onboarding` | bearer | Save the onboarding answers |
| `POST` | `/sync` | bearer | Push local record changes, pull changes after a cursor |
| `POST` | `/ai/career/:task` | bearer | Career AI: `read-job`, `parse-line`, `nudge`, `interview-prep`, `skill-path` |
| `GET` | `/ai/status` | bearer | Whether the AI service is reachable |
| `POST` | `/ai/assist` | bearer | Free-form AI assist (not used by the app yet) |

The API also serves password sign-in, magic links, TOTP, passkeys, Google sign-in and session
management under `/auth`, `/auth/methods` and `/auth/security`. The app does not use them yet, so
they are documented in Swagger (`/api/docs`) rather than here; each moves into this table when a
client adopts it.

### Profile

`PATCH /users/me/profile` takes any of `username` (3–64 chars, `a-z 0-9 . _ -`), `displayName`
(≤100), `avatarUrl`, `bio` (≤280), `timezone`, `locale`; unknown keys are rejected and at least one
field is required. `POST /users/me/avatar` accepts JPEG, PNG or WebP up to 2 MB and returns the updated
profile. Avatars are currently stored on the API container's disk, which is not durable in
production (see [Product System Design](/docs/product-system-design), section 6).

### Email-code sign-in

`POST /auth/methods/email-code/request`, throttled to 3 per minute:

```json
{ "email": "you@example.com", "name": "Shabir" }
```

`name` is optional and only used when the account is created. The response is always `202`
`{ "accepted": true, "message": "A sign-in code has been sent." }`, whether or not the account
existed; outside production it also carries `developmentCode`.

`POST /auth/methods/email-code/verify`, throttled to 8 per minute:

```json
{ "email": "you@example.com", "code": "123456" }
```

`200` returns the session `{ accessToken, accessTokenExpiresAt, refreshToken (native only), user }`
and marks the email verified. A wrong or expired code returns `401` `AUTH_OTP_INVALID`; codes
lock after the configured number of attempts.

### Onboarding answers

`PUT /users/me/onboarding` takes `{ "answers": OnboardingAnswers }`, the same shape as the mobile
store (`apps/mobile/src/modules/onboarding/store/onboarding-store.ts`). Unknown keys and
out-of-range values are rejected with `400`. Both endpoints return
`{ answers, schemaVersion, updatedAt }`, and `GET` returns `null` before the first save.

The plan is not stored: the app derives it from the answers. When the stored row no longer matches
the current schema, `GET` returns `null` and the app uploads its copy. After sign-in the app keeps
whichever side changed last (`updatedAt` against the device's own timestamp), then uploads changes
about a second after they happen.

### Sync

`POST /sync`, throttled to 60 per minute, body up to 1 MB:

```json
{
  "cursor": "1834",
  "changes": [
    {
      "collection": "career-applications",
      "id": "lz3k9q-4f2a1b",
      "data": { "id": "lz3k9q-4f2a1b", "company": "Tessera" },
      "updatedAt": 1760486400000,
      "deletedAt": null
    }
  ]
}
```

`cursor` is `null` on the first sync. `collection` is lower-kebab-case (≤ 64), `id` is
`[A-Za-z0-9_-]{1,64}`, `data` any JSON up to 64 KB, `updatedAt`/`deletedAt` milliseconds. At most
200 changes, one per record. `200` returns:

```json
{ "cursor": "1902", "changes": [/* records changed after the cursor */], "conflicts": [], "hasMore": false }
```

- A change is kept when its `updatedAt` is newer than the stored copy. Otherwise the stored copy
  is returned in `conflicts` and the client should take it.
- `changes` may include records the client just pushed; applying them is harmless.
- Keep calling with the returned cursor while `hasMore` is `true` (pages of 500).
- `400` `SYNC_CLOCK_AHEAD` when a change is dated more than a day in the future;
  `400` `SYNC_DUPLICATE_RECORD` when one record appears twice.

Collections in use: `career-applications`, `career-preps`, `career-stories`, `career-flashcards`,
`career-skill-plans`, `career-skill-sessions`, `career-settings`. Names are part of the contract.

### Career AI

`POST /ai/career/:task`, throttled to 20 per minute. The body is validated by the AI service;
field names are snake_case.

| Task | Body | Returns |
| --- | --- | --- |
| `read-job` | `{ url }` or `{ text }` (≤ 20,000 chars) | `{ company, role, pay, where, summary, halal: { status, note } }` |
| `parse-line` | `{ text, today: "YYYY-MM-DD" }` | `{ application: { company, role, pay, where, stage, halal } \| null, follow_up_in_days, interview_at }` |
| `nudge` | `{ sender_name, company, role, contact_name, days_since_applied, notes, stories[], tone, current_draft? }` | `{ subject, body }` |
| `interview-prep` | `{ company, role, round, notes, stories[] }` | `{ topics[{ title, detail }], questions[], flashcards[{ topic, tag, front, back, code }] }` |
| `skill-path` | `{ focus, weeks, context }` | `{ title, weeks[{ title, goal, days[5]{ title, detail } }] }` |

`halal.status` is `clean`, `flagged` or `unsure`; it is the model's reading, which the person
confirms. `tone` is `as-is`, `shorter`, `warmer` or `formal`. Errors: `422` `JOB_LINK_UNREADABLE`
(sign-in wall, blocked, private address, too large), `400` `VALIDATION_ERROR`, `502`
`AI_INVALID_OUTPUT` / `AI_UPSTREAM_ERROR`, `503` `AI_UNAVAILABLE`.
