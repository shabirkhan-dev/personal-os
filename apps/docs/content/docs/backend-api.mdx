This page is the one place the API contract lives (`apps/api`, Hono on Cloudflare Workers). The agent contract in
`.agents/agent-contract.md` points every role here: web and mobile read it before consuming an
endpoint, and backend updates it in the same commit as any public API change.

Endpoints are listed here as clients start using them. A contract that lives in one file stays
consistent; one scattered across cards and notes drifts immediately.

## What belongs here

- Every public endpoint: method, path, auth requirement, request and response shape.
- The response envelope, error shape and status-code conventions.
- Pagination, filtering and sorting conventions.
- Breaking changes, with a dated changelog entry below.

## What does not

- Implementation detail, internal service structure, database schema.
- Anything still being designed — raise a boa## Endpoints

All paths are under `/api/v1`. Bodies are JSON. Signed-in routes take
`Authorization: Bearer <accessToken>`.

Every success is `{ success: true, statusCode, requestId, timestamp, data }`; the app reads
`data`. Every failure is
`{ success: false, statusCode, code, message, requestId, timestamp, path, method, errors? }`.
`code` is stable and is what clients branch on; `message` is a sentence that can be shown as is;
`errors` lists `{ path, message }` for `VALIDATION_FAILED`. Codes and statuses come from one
table, `apps/api/src/config/messages.ts`.

| Method | Path | Auth | Purpose |
| --- | --- | --- | --- |
| `GET` | `/health` | none | Liveness, environment, AI provider, whether uploads are set up |
| `POST` | `/auth/email-code/request` | none | Send a 6-digit sign-in code |
| `POST` | `/auth/email-code/verify` | none | Exchange the code for a session; creates the account on first use |
| `POST` | `/auth/refresh` | refresh token | Rotate the session |
| `POST` | `/auth/logout` | refresh token | End the session (`204`) |
| `GET` | `/users/me` | bearer | Current user |
| `PATCH` | `/users/me/profile` | bearer | Update the display name or avatar |
| `POST` | `/assets/uploads` | bearer | A presigned URL to upload a file straight to R2 |
| `GET` | `/users/me/onboarding` | bearer | Saved onboarding answers, or `null` before the first save |
| `PUT` | `/users/me/onboarding` | bearer | Save the onboarding answers |
| `POST` | `/sync` | bearer | Push local record changes, pull changes after a cursor |
| `POST` | `/ai/career/<task>` | bearer | Career AI: `read-job`, `parse-line`, `nudge`, `interview-prep`, `skill-path` |

Rate limits (per IP, or per user when signed in, per minute): auth routes 10, `/sync` 60, AI 20.
Over the limit: `429` `RATE_LIMITED`. When the Worker's settings are incomplete, every route
answers `503` `CONFIG_INVALID`, naming the missing settings (never their values). Bodies over 1 MB (AI: 32 KB): `413` `BODY_TOO_LARGE`.

### Sign-in

`POST /auth/email-code/request`:

```json
{ "email": "you@example.com", "name": "Shabir" }
```

`202` `{ accepted: true, message }`, the same whether or not the email has an account. `name` is
used only if the code creates the account. Outside production, without an email key, the
response also has `developmentCode`. A new code replaces the previous one.

`POST /auth/email-code/verify` with `{ email, code }` returns `200`:

```json
{
  "accessToken": "eyJ…",
  "accessTokenExpiresAt": "2026-10-15T10:15:00.000Z",
  "refreshToken": "<session id>.<secret>",
  "user": { "id": "…", "email": "you@example.com", "displayName": "Shabir", "avatarUrl": null, "createdAt": "…" }
}
```

The account is created on the first successful code. A wrong, used or expired code is `401`
`AUTH_CODE_INVALID`; a code stops working after 5 wrong tries. Access tokens last 15 minutes;
sessions last 30 days from the last refresh.

`POST /auth/refresh` with `{ refreshToken }` returns a new session (same shape) and a new refresh
token. Presenting an old refresh token again ends the session (`401`
`AUTH_REFRESH_TOKEN_INVALID`), since it means the token was copied. `POST /auth/logout` with
`{ refreshToken }` answers `204` either way.

Signed-in routes answer `401` with `AUTH_REQUIRED` (no token), `AUTH_ACCESS_TOKEN_INVALID`
(expired or malformed) or `AUTH_SESSION_INVALID` (session ended).

### Profile and avatar

`PATCH /users/me/profile` takes `displayName` (≤ 100, or `null`) and/or `avatarKey`, and returns
the user. Avatars never pass through the API:

1. `POST /assets/uploads` with `{ "kind": "avatar", "contentType": "image/jpeg" }` (`image/png`
   and `image/webp` also allowed) returns `201`
   `{ key, uploadUrl, method: "PUT", headers, expiresAt }`. The URL is valid for 10 minutes.
2. The app `PUT`s the file to `uploadUrl` with exactly those `headers`.
3. `PATCH /users/me/profile` with `{ "avatarKey": key }`. The API checks the object is in R2,
   under the caller's prefix, an allowed type and at most 5 MB, then saves it and deletes the
   previous avatar. `avatarUrl` in the user is the public URL.

Errors: `400` `ASSET_NOT_UPLOADED` (nothing at that key), `400` `ASSET_INVALID` (wrong prefix,
type or size; a bad file is deleted), `503` `ASSETS_UNAVAILABLE` (R2 not configured).
`"avatarKey": null` removes the avatar.

### Onboarding answers

`PUT /users/me/onboarding` takes `{ "answers": OnboardingAnswers }`, the same shape as the mobile
store (`apps/mobile/src/modules/onboarding/store/onboarding-store.ts`). Unknown keys and
out-of-range values are rejected with `400`. Both endpoints return
`{ answers, schemaVersion, updatedAt }`, and `GET` returns `null` before the first save.

The plan is not stored: the app derives it from the answers. When the stored row no longer matches
the current schema, `GET` returns `null` and the app uploads its copy. After sign-in the app keeps
whichever side changed last (`updatedAt` against the device's own timestamp), then uploads changes
about a second after they happen.

### Sync

`POST /sync`:

```json
{
  "cursor": "1834",
  "changes": [
    {
      "collection": "career-applications",
      "id": "lz3k9q-4f2a1b",
      "data": { "id": "lz3k9q-4f2a1b", "company": "Tessera" },
      "updatedAt": 1760486400000,
      "deletedAt": null
    }
  ]
}
```

`cursor` is `null` on the first sync. `collection` is lower-kebab-case (≤ 64), `id` is
`[A-Za-z0-9_-]{1,64}`, `data` any JSON up to 64 KB, `updatedAt`/`deletedAt` milliseconds. At most
200 changes, one per record. `200` returns:

```json
{ "cursor": "1902", "changes": [/* records changed after the cursor */], "conflicts": [], "hasMore": false }
```

- A change is kept when its `updatedAt` is newer than the stored copy. Otherwise the stored copy
  is returned in `conflicts` and the client should take it.
- `changes` may include records the client just pushed; applying them is harmless.
- Keep calling with the returned cursor while `hasMore` is `true` (pages of 500).
- `400` `SYNC_CLOCK_AHEAD` when a change is dated more than a day in the future;
  `400` `SYNC_DUPLICATE_RECORD` when one record appears twice.

Collections in use: `career-applications`, `career-preps`, `career-stories`, `career-flashcards`,
`career-skill-plans`, `career-skill-sessions`, `career-settings`. Names are part of the contract.

### Career AI

`POST /ai/career/<task>`. Field names are camelCase. Answers are checked against a schema before
they are returned: long text is trimmed, and an answer of the wrong shape is an error rather than
reaching the app.

| Task | Body | Returns |
| --- | --- | --- |
| `read-job` | `{ url }` or `{ text }` (≤ 20,000 chars) | `{ company, role, pay, where, summary, halal: { status, note } }` |
| `parse-line` | `{ text, today: "YYYY-MM-DD" }` | `{ application: { company, role, pay, where, stage, halal } \| null, followUpInDays, interviewAt }` |
| `nudge` | `{ senderName, company, role?, contactName?, daysSinceApplied, notes?, stories?, tone?, currentDraft? }` | `{ subject, body }` |
| `interview-prep` | `{ company, role?, round?, notes?, stories? }` | `{ topics[{ title, detail }], questions[], flashcards[{ topic, tag, front, back, code }] }` |
| `skill-path` | `{ focus, weeks?, context? }` | `{ title, weeks[{ title, goal, days[5]{ title, detail } }] }` |

`stories` is up to 6 `{ title, summary }`. `halal.status` is `clean`, `flagged` or `unsure`; it is
the model's reading, which the person confirms. `tone` is `as-is`, `shorter`, `warmer` or
`formal`. Errors: `422` `JOB_LINK_UNREADABLE` (sign-in wall, blocked, private address, too large;
the message says which), `400` `VALIDATION_FAILED`, `502` `AI_INVALID_OUTPUT`, `503`
`AI_UNAVAILABLE`.

, `503` `AI_UNAVAILABLE`.
