This page replaces the old one-off upgrade report. Dependency versions change; the package manifests
and `bun.lock` are the current inventory. Do not use a dated table as proof that a package is still
installed or safe to upgrade.

## Before changing a dependency

1. Identify the owning workspace (`apps/web`, `apps/mobile`, `apps/nest-api`, `apps/docs`,
   `apps/ai-api`, `apps/rust`, or a package).
2. Read its release notes and compatibility requirements, especially for Expo, Next.js, NestJS, and
   Rust toolchains.
3. Check whether the dependency participates in the root `overrides` block.
4. Search for direct imports, configuration, and generated files before changing the API.

## Preferred commands

```bash
bun outdated --recursive
bun install
bun --cwd=apps/docs run types:check
bun --cwd=apps/web run typecheck
bun --cwd=apps/mobile run lint
bun --cwd=apps/nest-api run typecheck
bun --cwd=apps/nest-api run test
bun --cwd=apps/ai-api run test
bun run build
git diff --check
```

For Python, use the scripts in `apps/ai-api` so `uv` resolves the project environment. For Rust,
run `cargo update` only with a reviewed lockfile diff, then run `cargo test` and `cargo clippy`.

## Upgrade policy

- Keep framework upgrades isolated from feature work.
- Upgrade Expo packages with the Expo SDK compatibility matrix, not arbitrary latest versions.
- Keep React, React DOM, React Native, and React Native Web compatible with their app framework.
- Treat database drivers, auth libraries, and payment SDKs as security-sensitive upgrades.
- Regenerate ORM artifacts only when the owning app's documented command succeeds.
- Review the lockfile for unexpected packages, postinstall scripts, or registry changes.

## Record the result

The change description should include the workspace, old and new range, reason, verification, and
any deferred upgrade. If a host cannot access a registry or tool cache, say so explicitly and leave
the dependency unchanged rather than presenting an incomplete upgrade as complete.
