Where each piece of Personal OS runs in production:

| App | Platform | Notes |
|-----|----------|--------|
| `apps/api` | [Cloudflare Workers](https://workers.cloudflare.com) | Hono; Neon through Hyperdrive, R2 for images, rate limiting |
| `apps/mobile` | [EAS](https://expo.dev/eas) | Builds and over-the-air updates; see `apps/mobile/README.md` |
| `apps/web` | [Cloudflare Workers](https://workers.cloudflare.com) | Next.js static export served as Worker assets + `/api/notify` |
| `apps/docs` | [Vercel](https://vercel.com) | Separate Vercel project |
| Database | [Neon](https://neon.tech) | Serverless Postgres |

Repo files: `apps/api/wrangler.jsonc`, `apps/web/README.md`, `apps/docs/vercel.json`.

**Cost.** The Workers Free plan is enough to try it. The Workers Paid plan ($5/month) is the one to
run on: it raises the CPU limit per request from 10 ms (a large sync can need more) and its
allowance (10 million requests a month) covers a handful of users with nothing extra. Neon's and
R2's free tiers cover the database and images; the AI provider bills per use.

All commands below run from the repo root and need `bunx wrangler login` once.

## 1) Neon database

1. Create a project at [console.neon.tech](https://console.neon.tech).
2. Copy the **direct** connection string (not the pooled one: Hyperdrive does the pooling). It
   ends in `sslmode=require`.
3. Apply the migrations:

   ```bash
   DATABASE_URL="<Neon URL>" bun --cwd=apps/api run db:migrate
   ```

   Run this again whenever a pull request adds a file under `apps/api/src/db/migrations`.

## 2) The API on Cloudflare Workers

### Hyperdrive (the database connection)

```bash
bunx wrangler hyperdrive create personal-os-db --connection-string="<Neon URL>"
```

Paste the printed `id` into `hyperdrive[0].id` in `apps/api/wrangler.jsonc`.

### R2 (images)

1. Create the bucket: `bunx wrangler r2 bucket create personal-os-assets`.
2. **Public reads:** in the dashboard, R2 → `personal-os-assets` → Settings → Public access, connect
   a custom domain (for example `assets.your-domain.com`). The `r2.dev` address works for testing
   but is rate limited.
3. **Upload credentials:** R2 → Manage API tokens → Create API token, permission *Object Read &
   Write*, limited to this bucket. Keep the Access Key ID and Secret Access Key.
4. Set the variables `R2_ACCOUNT_ID` (your account id, on the R2 overview page) and
   `R2_PUBLIC_URL` (the public domain, no trailing slash) as described below.

The app uploads straight to R2 with a presigned URL; the API only checks and saves the key. No
bucket CORS rule is needed for the app (CORS only applies to browsers).

### Settings and secrets

The repo is public, so `wrangler.jsonc` holds only generic settings. Values for your own
deployment are dashboard **variables** (Worker → Settings → Variables and Secrets → Add, type
*Text*); `keep_vars` in `wrangler.jsonc` stops a deploy from deleting them:

| Variable | Example |
|---|---|
| `AUTH_EMAIL_FROM` | `Personal OS <auth@your-domain.com>`, on a domain verified in [Resend](https://resend.com) |
| `OPENAI_BASE_URL` | `https://api.deepseek.com` |
| `OPENAI_MODEL` | `deepseek-flash` (DeepSeek V4.1 Flash) |
| `R2_ACCOUNT_ID` | your Cloudflare account id |
| `R2_PUBLIC_URL` | `https://assets.your-domain.com` |

The AI key goes in the `OPENAI_API_KEY` secret whatever the provider; any OpenAI-compatible
provider works by changing the two `OPENAI_*` variables. In production the Worker refuses to
start while `AUTH_EMAIL_FROM` is still an `example.com` address.

Then the secrets, each prompted for its value:

```bash
cd apps/api
openssl rand -base64 48 | bunx wrangler secret put JWT_SECRET
openssl rand -base64 48 | bunx wrangler secret put AUTH_TOKEN_SECRET
bunx wrangler secret put RESEND_API_KEY
bunx wrangler secret put OPENAI_API_KEY
bunx wrangler secret put R2_ACCESS_KEY_ID
bunx wrangler secret put R2_SECRET_ACCESS_KEY
```

The Worker refuses to start in production without real `JWT_SECRET`, `AUTH_TOKEN_SECRET` and
`RESEND_API_KEY`, and `AI_PROVIDER=openai_compatible` needs `OPENAI_API_KEY`. Changing a secret
needs no app rebuild.

**Crash reports (optional).** Create a project at [sentry.io](https://sentry.io) (platform:
JavaScript) and set its DSN as the `SENTRY_DSN` secret (`bunx wrangler secret put SENTRY_DSN`);
optionally a `RELEASE` variable such as `api@0.5.0`. Unexpected 500s and a failed daily cleanup
are then reported with the route, method and request id only, never request bodies. Without the
DSN nothing is sent. The reporter is a few lines in `@personal-os/domain/error-report` (Sentry's
envelope format over `fetch`), so no SDK ships in the Worker.

API answers carry `Cache-Control: no-store` (personal data never sits in a cache), Hono's secure
headers and a request id; each area has its own rate limit (`ratelimits` in `wrangler.jsonc`).

### Deploy

Either connect GitHub once: Workers & Pages → Create → Import a repository → this repo, root
directory `apps/api`, deploy command `npx wrangler deploy` (every push to `main` then deploys), or
deploy from your machine:

```bash
bun --cwd=apps/api run deploy
```

Check it:

```bash
curl -sS https://personal-os-api.<your-subdomain>.workers.dev/api/v1/health
# "environment": "production", "ai": "openai_compatible", "assets": "ready"
curl -sS --fail https://personal-os-api.<your-subdomain>.workers.dev/api/v1/ready
# 200 once the database answers; point an uptime monitor here
```

`ai: "off"` means the provider key is missing: AI screens say AI is unavailable and everything
else keeps working. The Worker also runs a daily cron (`triggers.crons` in `wrangler.jsonc`) that
drops old sign-in codes, ended sessions and old AI usage.

**Order matters when a pull request adds a migration:** apply it to Neon first, then let the
Worker deploy. CI fails a pull request whose schema changed without a migration.

### CD: migrations and a smoke check

`.github/workflows/cd.yml` runs on every push to `main`: the full quality gate (lint, typecheck,
tests against Postgres), then the migrations, then a smoke check that waits for the new Worker
to answer `/api/v1/ready` and `/api/v1/health`. In the repository's **Settings → Secrets and
variables → Actions** add:

| Kind | Name | Value |
|---|---|---|
| Secret (environment `production`) | `DATABASE_URL` | the Neon connection string (direct, not pooled) |
| Variable | `API_URL` | the API origin, e.g. `https://api.your-domain.com` |

Without them the two jobs skip with a notice. Workers Builds keeps deploying the Worker itself;
the migration job runs right after the gate, so add a migration's schema change in a backwards
compatible way (new nullable column first, use it in the next release).

### Staging

A staging Worker needs its own database so tests never touch real data:

1. In Neon, create a branch `staging` from `main` and copy its connection string.
2. Create a Hyperdrive config for it (`bunx wrangler hyperdrive create personal-os-staging
   --connection-string="<staging URL>"`).
3. Add to `wrangler.jsonc`, with that id:

```jsonc
"env": {
	"staging": {
		"name": "personal-os-api-staging",
		"vars": { "ENVIRONMENT": "production", "APP_NAME": "Personal OS (staging)", "AI_PROVIDER": "openai_compatible", "R2_BUCKET_NAME": "personal-os-assets-staging" },
		"hyperdrive": [{ "binding": "HYPERDRIVE", "id": "<staging hyperdrive id>" }],
		"r2_buckets": [{ "binding": "ASSETS", "bucket_name": "personal-os-assets-staging" }],
		"ratelimits": [ /* copy the four limiters with new namespace ids, e.g. 5101–5104 */ ]
	}
}
```

4. Set its secrets with `--env staging` and deploy with `bunx wrangler deploy --env staging`.
   Point a preview build at it with `EXPO_PUBLIC_API_URL` in the EAS `preview` environment.

### Branch protection

In GitHub **Settings → Branches → Add rule** for `main`: require a pull request, require the
status checks `lint`, `typecheck`, `test` and `build` to pass, and block force pushes and
deletions. Only the repository owner can set this.

**Backups:** Neon keeps point-in-time history; check the retention window in the Neon project
settings and restore to a branch to recover (Neon → Branches → restore). Migrations have no
down step, so a bad one is undone by restoring, not by rolling back.

## 3) The app on EAS

1. On expo.dev, the project → **Settings → GitHub**: connect this repo, base directory
   `apps/mobile`.
2. **Environment variables:** add `EXPO_PUBLIC_API_URL` = the Worker URL (https, no path) to the
   `preview` and `production` environments (`eas env:create`). It is baked in at build time; a
   production build without an https URL stops before installing, and a release app without one
   says it can't reach its server instead of calling localhost.
3. Build from the GitHub tab, or `bunx eas-cli build --profile preview --platform android` for a
   standalone APK.
4. **Crash reports (optional):** add `EXPO_PUBLIC_SENTRY_DSN` (a Sentry project DSN, it is a
   public value) to the same environments. Release builds then report crashes and screen errors
   with the app version and platform, never records. Unset, nothing is sent.

### APK on GitHub Releases

Anyone can install the app from the repository's **Releases** page, no store needed. The
`Release` workflow (`.github/workflows/release.yml`) builds one APK for every Android device
(arm64-v8a, armeabi-v7a, x86_64 and x86, the `release` profile in `apps/mobile/app.config.js`),
signs it with the project's release key, checks the signature and every architecture with
`apksigner`, attaches it with a SHA-256 checksum, and writes install steps and the certificate's
fingerprint into the release notes.

```bash
# bump "version" in apps/mobile/app.json first, then:
git tag v0.7.0
git push origin v0.7.0
```

Or run **Actions → Release → Run workflow** with a tag name (it creates the tag on the chosen
branch). Tags with a suffix (`v0.8.0-beta.1`) are marked as pre-releases. The app talks to the API
in the `API_URL` repository variable.

#### The release key

Releases are signed with one PKCS12 key (alias `personal-os`), so each release installs over the
last one and keeps the data. The workflow refuses to publish without it. It lives only in two
repository secrets (Settings → Secrets and variables → Actions):

| Secret | Value |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | the keystore, base64-encoded (`base64 -w0 personal-os-release.p12`) |
| `ANDROID_KEYSTORE_PASSWORD` | its password (the key uses the same one) |

`apps/mobile/plugins/with-release-signing.js` adds the signing config to the generated project and
uses it whenever `ANDROID_KEYSTORE_PATH` is set; local and E2E builds stay on the debug key.

Keep a copy of the keystore and its password somewhere safe outside GitHub. If it's lost, no
future APK can update an installed one: everyone would have to uninstall and reinstall.

To make a new key (only for a fork, or if the old one is lost):

```bash
keytool -genkeypair -storetype PKCS12 -keystore personal-os-release.p12 -alias personal-os \
  -keyalg RSA -keysize 4096 -validity 36500 -dname "CN=Personal OS, O=Personal OS"
```

Builds before the release key were signed with Expo's shared debug key. Android won't update
across keys, so moving from one of those means exporting a backup, uninstalling, installing and
importing it. A store build uses its own key through EAS, so switching between a store build and
the APK also needs an uninstall.

## 4) Landing page on Cloudflare Workers

`apps/web` is a static export (`out/`) served as Worker static assets, plus a small Worker for
launch-day sign-ups (`/api/notify`, Workers KV). It does not call the API.

1. **Workers & Pages → Create → Workers → Import a repository**, this repo, branch `main`.
2. Root directory `apps/web`, build command `bun run build`, deploy command `npx wrangler deploy`.
3. Create a KV namespace and put its id in `apps/web/wrangler.jsonc` (`WAITLIST` binding).
4. Add a custom domain, for example `personalos.your-domain.com`.

Full steps: `apps/web/README.md`.

## 5) Docs on Vercel

1. **Add another project** from the same repo.
2. **Root Directory:** `apps/docs`.
3. Env (optional, for docs AI chat):

| Variable | Value |
|----------|--------|
| `OPENROUTER_API_KEY` | from [OpenRouter](https://openrouter.ai) |
| `OPENROUTER_MODEL` | e.g. `anthropic/claude-3.5-sonnet` |

4. Deploy. Docs do not call the API.

- [ ] Migrations applied to Neon

- [ ] R2 bucket with a public domain; `R2_ACCOUNT_ID`, `R2_PUBLIC_URL` and the two R2 secrets set
- [ ] `AUTH_EMAIL_FROM` on a verified Resend domain; `RESEND_API_KEY` set
- [ ] `JWT_SECRET`, `AUTH_TOKEN_SECRET`, `OPENAI_API_KEY` set
- [ ] `/api/v1/health` shows production, `openai_compatible` and `assets: ready`
- [ ] `/api/v1/ready` answers 200, with an uptime monitor on it
- [ ] EAS `preview` and `production` environments have an https `EXPO_PUBLIC_API_URL`
- [ ] `API_URL` repository variable set, then a `v*` tag pushed for the GitHub release APK
- [ ] Neon point-in-time restore retention checked
- [ ] Branch protection on `main` requires lint, typecheck, build and test
- [ ] `DATABASE_URL` secret and `API_URL` variable set for CD (migrations and smoke check)
- [ ] `SENTRY_DSN` (Worker) and `EXPO_PUBLIC_SENTRY_DSN` (EAS) set if you want crash reports
- [ ] Privacy policy at `/privacy` and terms at `/terms` on the landing domain (Play Console needs the URL)
- [ ] Email-code sign-in works on a device
- [ ] Landing page live on its custom domain, waitlist KV bound
- [ ] Docs project live (optional OpenRouter)
