---
title: Development Workflow
description: How a change goes from a card to main.
---

## 1) Claim a card

Work starts from a card in `.agents/board/` (see `.agents/README.md`). The card names the scope;
write only inside it.

## 2) Branch

`main` is integration only. Branch from it as `agent/<role>/<card-slug>` (for example
`agent/mobile/training-programs`), or `docs/<topic>` and `fix/<topic>` for small changes. Keep one
concern per branch, and keep formatting-only changes out of feature commits.

## 3) Commit

Lefthook runs on every commit: format, lint, typecheck, the architecture and naming checks, a
secret scan and a 2 MB large-file guard. Messages follow Conventional Commits, all lowercase:

```text
feat(training): programs with double progression
fix(api): limit sign-in codes to one a minute
```

Stage explicit paths rather than `git add -A`. A file over 2 MB that belongs in the repo (the
README showcase video) is committed with `LEFTHOOK_EXCLUDE=large-files git commit ...`.

## 4) Check before pushing

```bash
bun run preflight
```

`preflight` runs lint, typecheck and every test (the API's against the local Postgres). Changed
the API? Update [Backend API](/docs/backend-api) in the same commit. Changed the database schema?
Commit the generated migration (`bun --cwd=apps/api run db:generate`); CI fails without one.

## 5) Pull request and merge

Open a PR into `main` with what changed, why, and how it was tested, and record the validation on
the card. CI runs lint, typecheck, build and tests; merge when it is green, then delete the
branch so `main` stays the only long-lived branch.

## 6) Ship

- **API**: Workers Builds deploys `apps/api` on every push to `main` once the repo is connected,
  or `wrangler deploy` from your machine; apply migrations first ([Deploy](/docs/deploy)).
- **App**: an EAS build (see the README's "Build the Android app") or an EAS Update for JS-only
  changes.
