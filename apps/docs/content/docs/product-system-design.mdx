Status: working blueprint for Personal OS. This page describes the direction of the current
repository; implementation readiness belongs in [Backend API](/docs/backend-api).

## Product shape

Personal OS is a personal-first system for routines, finance, personal care, food, fashion, and a
unified view of daily life. The system should feel calm and useful before it feels intelligent.

```text
Web / Mobile
     │
     ▼
NestJS API (/api/v1)
     │
 ┌───┴───────────────┐
 ▼                   ▼
PostgreSQL       Internal AI API
(source of truth) (optional provider adapter)
```

Clients never receive provider keys and never bypass Nest to call the AI service. The API owns
identity, authorization, validation, response envelopes, and the contract consumed by web and
mobile.

## Architectural defaults

### One modular API first

Keep product modules inside `apps/nest-api/src/modules/` while the data model and ownership rules
are evolving. A module should make its controller, service, repository, schema, and tests easy to
find. Extract a service only when a measured boundary makes the system safer or easier to own.

### One database source of truth

PostgreSQL stores user-owned product data. Drizzle migrations are reviewed artifacts. Data access
must be scoped to the authenticated user, and dates representing a user's day must use their
profile timezone rather than the server timezone.

### Thin clients, explicit state

Web and mobile should compose product workflows, not recreate business rules. API clients unwrap the
standard response envelope and normalize auth refresh, loading, empty, and error states in one place.

### AI as an assistive boundary

AI may summarize, suggest, classify, or draft. It must not silently mutate durable user data or make
high-impact decisions. Important actions require user intent or confirmation, and prompts should be
grounded in the minimum data required for the task.

## Domain boundaries

| Domain | Owns | Does not own |
| --- | --- | --- |
| Identity | Sessions, credentials, passkeys, MFA, social sign-in | Product-specific routine or finance rules |
| Profile | User preferences, timezone, avatar, personal settings | Authentication secrets |
| Routines | Schedules, ordered items, daily completion | Finance transactions or AI provider state |
| Finance | Transactions, budgets, summaries, categories | Routine completion semantics |
| Care/Food/Fashion | Future domain records and workflows | Generic identity/session behavior |
| AI | Internal provider adapter and model-facing execution | Public auth, authorization, or direct client access |

Cross-domain views should read stable module contracts. Avoid a giant shared table that couples every
future product idea to every other domain.

## Security and privacy defaults

- Use httpOnly cookies and short-lived access tokens according to the auth contract.
- Validate and authorize every resource by user ownership.
- Keep secrets in environment configuration; never send them to web or mobile.
- Treat finance and personal-care data as sensitive; minimize logs and telemetry payloads.
- Use rate limits, secure headers, CORS allowlists, and explicit production cookie settings.
- Make mutation endpoints idempotent where retries are expected.
- Record security-relevant events without storing raw credentials or provider tokens.

## Contract rules

- Public routes are under `/api/v1`.
- Responses use the documented `{ success, statusCode, data }` success envelope and structured
  errors.
- Breaking changes require a migration note and either a new version or an explicit changelog entry.
- Dates are `YYYY-MM-DD` in the user's timezone when they represent a user day.
- ISO weekdays use `1 = Monday` through `7 = Sunday`.
- The backend agent updates `apps/docs/content/docs/backend-api.mdx` in the same commit as API work.

## Review questions

Before merging a design or implementation, ask:

1. Which module owns this behavior and its data?
2. Can a user access another user's record through any identifier, filter, or summary?
3. What happens when the request is retried, refreshed, offline, empty, or partially complete?
4. Does this add a contract that web and mobile both need to understand?
5. Is AI being used as a reversible assistant rather than an invisible authority?
6. Is the new boundary enforced by tests, architecture checks, or a documented decision?
