## 1. What the system is

Personal OS is a **single-person, mobile-first** app. One account belongs to one person; there
are no organizations, workspaces, teams or roles. The Expo app is the product. The servers exist
for sign-in, backing up what the person tells the app, and AI assistance.

Principles:

- **The phone works on its own.** Logging an expense, a meal or a workout never waits on the
  network.
- **Private by default.** The data is personal (money, body, routines). The server keeps only what
  it needs, and AI never sees data the person has not chosen to share.
- **One person, scoped by `userId`.** Every server row belongs to exactly one user.
- **Stateless servers.** API containers keep no session or file state that a restart would lose
  (see the avatar gap in section 6).

## 2. High-level architecture

```text

 │  SecureStore ──► session tokens             │
```

## 3. Mobile app

| Path | Responsibility |
| --- | --- |
| `src/app/(onboarding)` | Onboarding flow: about you, body, goals, your day, modules, reminders, plan reveal, sign-in |
| `src/app/(home)` | Today (Overview or one module Home), Calendar, Profile and each module's inner screens |
| `src/modules/<name>` | One folder per feature: `components`, `hooks`, `lib` (pure logic, tested), `services` (I/O), `store` |
| `src/lib/storage` | `createDocumentStore`: a Zustand store backed by one JSON file, for small device-only state |
| `src/lib/api` | Typed fetch client, token refresh |
| `src/components`, `src/theme` | Kit v2 components and the theme provider over `@personal-os/tokens` |

Modules on the Home: Daily life, Training, Career, Finance, Food, Care, Faith, Fashion and Wishlist.
Each module Home reads its own collections; the ask bar parses typed lines ("500 food", "45 min
gym") into entries for the right module. The Calendar reads every module's dated items (training
sessions and program weeks, interviews and follow-ups, bill due days) next to the person's own
events.

### On-device data

- **Record store** (every module): one SQLite database with typed collections, read through React
  Query and backed up by sync. Works offline; writes are instant. See
  [ADR 0002](/docs/architecture/adr-0002-offline-first-sync).
- **JSON documents** (device-only state such as the chosen Home view, the profile cache and a live
  training session): one small file each, hydrated on first use with debounced writes. See
  [ADR 0001](/docs/architecture/adr-0001-on-device-module-data).

Profile → Export writes every record in the on-device database to one file.

Both parse what they read, so old or damaged data never crashes a screen. Secrets (refresh token)
go in SecureStore, never in either store.

### Career

Career Home shows runway (cash on hand ÷ monthly costs, the costs estimated from Finance when not
set), the pipeline by stage, follow-ups due, recent activity, the next interview and the skill
block. Inner screens: applications by stage, application detail with a status timeline,
interview prep, flashcards (spaced review) and the skill path. The ask bar logs a line ("applied
to tessera, senior typescript, 500k, remote") through AI, or with an on-device parser offline.

## 4. API

`apps/api` is one Hono app on Cloudflare Workers
([ADR 0003](/docs/architecture/adr-0003-one-api-on-workers)). Each feature is a module
(`src/modules/<name>`: routes, service, repository, zod schemas). Zod checks every request and the
environment; every error is an `AppError` whose code, status and message come from one table
(`src/config/messages.ts`); every answer uses the same envelope. The contract lives in
[Backend API](/docs/backend-api).

The app uses all of it: email-code sign-in, refresh and logout, `GET /users/me` and the profile,
account deletion (`DELETE /users/me`), presigned uploads, onboarding answers, `POST /sync` and the
module AI tasks. A daily cron drops old sign-in codes, ended sessions and old AI usage. Sign-in is
email code only (Google, passwords, TOTP and passkeys were removed; pos-12 closed).

### Data model

| Table | Purpose |
| --- | --- |
| `users` | Email, display name, avatar key (R2), active flag |
| `sessions` | Refresh sessions: hashed token, expiry, user agent, revocation |
| `sign_in_codes` | Email codes, hashed, keyed by email, with attempt counts |
| `onboarding_profiles` | The onboarding answers as JSON with a `schema_version`; the plan is derived on the device |
| `ai_usage` | AI calls per user per UTC day, for the daily allowance |
| `assistant_threads`, `assistant_messages` | Conversations with the assistant: the model's messages, tool calls and results, and the cards shown |
| `assistant_memories` | Short facts the assistant keeps about the person, which they can delete |
| `sync_records` | Every synced document: user, collection, id, JSON data, `updated_at`, `deleted_at`, and a `seq` that sync cursors page through |

Schema changes are made in `apps/api/src/db/schema` and committed with the generated migration
(`bun --cwd=apps/api run db:generate`); migrations are applied with `db:migrate` before deploying.

### Onboarding sync

After sign-in the app compares its own timestamp with the server's `updatedAt` and keeps whichever
changed last, then uploads changes about a second after they happen. A stored row from an older
schema version reads as `null`, and the app uploads its copy.

### Files

Images go to R2. The app asks `POST /assets/uploads` for a presigned URL whose signature covers
the exact type and length, uploads the file straight to R2, and sends back only the key; the API
checks the object (prefix, type, size) before saving it. Two kinds exist: `avatar` (up to 5 MB,
saved with the profile) and `media` (exercise photos and GIFs up to 15 MB, confirmed with
`POST /assets/confirm`, which returns the public URL). Videos are not copied: an exercise links a
Google Drive file and the app plays it in Drive's own player.

## 5. AI

AI runs only in the cloud, inside the API: an OpenAI-compatible provider in production (no local
models) and a deterministic mock for development and tests. The provider key is a Worker secret;
the app never holds it.

Every module has its tasks under `POST /ai/<module>/<task>`: Career (read a job post with a halal
reading, parse a line, draft a follow-up, interview prep, skill path), Training (ask, skill steps,
design a program from the app's exercises), Finance, Food, Fashion, Care, Faith and Wishlist. Each
asks the model for JSON matching a zod schema and validates the answer before it reaches the app.
Answers are capped at 4,000 tokens and each user has 150 AI calls a day; the app says plainly when
the allowance is used up or AI is off. Reading a link refuses local and private addresses on every
redirect, with size and time limits, and strips HTML in linear time.

### The assistant

One assistant answers from the person's own records instead of a fixed form per task. The app
streams a message to `POST /assistant/messages` with where the person is (module, screen,
record) and their time zone. The API runs a loop: the model reads the conversation and calls
tools; each tool reads or writes the person's synced records through the shared rules in
`@personal-os/domain`, then the model answers. Text, tool steps and cards (stats, records,
approvals, changes with Undo, choices) stream back as they happen.

Writes wait for the person's approval per their setting (every change, only risky ones, or none)
and can be undone. A write is a newer version in `sync_records`, so the phone pulls it like any
other change; the app syncs as soon as an answer that changed something finishes. Conversations
(`assistant_threads`, `assistant_messages`) and a short memory of facts about the person
(`assistant_memories`) are kept on the account. Career, Finance, Training, Food and Care have
tools today; the other modules get theirs next.

## 6. Security and known gaps

- Access tokens: JWT, 15 minutes. Refresh tokens: rotated on every refresh, stored hashed; reusing
  an old one ends the session, except a retry within a minute (a lost answer). The app keeps the
  refresh token in SecureStore and shares one refresh across requests.
- Email codes are hashed, single use, replaced by a newer code and locked after 5 wrong tries; one
  code a minute and ten a day per email. Responses do not reveal whether an account exists.
- Cloudflare rate limiting per IP or user (sign-in codes 10, sync 60, AI 20, upload tickets 5 per
  minute), secure headers, body size limits. Sync skips a bad record instead of failing the batch.
- Release builds refuse a non-HTTPS API address and never fall back to localhost.

Known gaps:

- **Some photos stay on the phone.** Wardrobe, meal and dream photos are not uploaded yet.
- **Last write wins per record.** Two devices editing the same record offline keep only the newer
  edit.

## 7. Direction under discussion (not built)

1. **One shared primitive under the daily modules.** `actions` (what, when, part of the minimum
   day) and `entries` (done or skipped, value, date) as collections, so streaks and "never miss
   twice" are computed once for every module.
2. **Files.** The remaining photos (wardrobe, meals, dreams, receipts) through the same R2 upload
   flow, with Cloudflare image resizing.
3. **AI with consent per module.** Insights read a compact daily digest of the modules the person
   has shared, and propose changes the person confirms.
4. **Reminders on the device.** Scheduled local notifications, so the most important nudges do not
   depend on the server.
