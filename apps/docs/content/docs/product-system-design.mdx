## 1. What the system is

Personal OS is a **single-person, mobile-first** app. One account belongs to one person; there
are no organizations, workspaces, teams or roles. The Expo app is the product. The servers exist
for sign-in, backing up what the person tells the app, and AI assistance.

Principles:

- **The phone works on its own.** Logging an expense, a meal or a workout never waits on the
  network.
- **Private by default.** The data is personal (money, body, routines). The server keeps only what
  it needs, and AI never sees data the person has not chosen to share.
- **One person, scoped by `userId`.** Every server row belongs to exactly one user.
- **Stateless servers.** API containers keep no session or file state that a restart would lose
  (see the avatar gap in section 6).

## 3. Mobile app

| Path | Responsibility |
| --- | --- |
| `src/app/(onboarding)` | Onboarding flow: about you, body, goals, your day, modules, reminders, plan reveal, sign-in |
| `src/app/(home)` | Today (Overview or one module Home), Profile, Recipes |
| `src/modules/<name>` | One folder per feature: `components`, `hooks`, `lib` (pure logic, tested), `services` (I/O), `store` |
| `src/lib/storage` | `createDocumentStore`: a Zustand store backed by one JSON file |
| `src/lib/api` | Typed fetch client, token refresh |
| `src/components`, `src/theme` | Kit v2 components and the theme provider over `@personal-os/tokens` |

Modules on the Home: Daily life, Workout, Finance, Skincare, Food, Fashion. Each module Home reads
its own document store; the ask bar parses typed lines ("500 food", "45 min gym") into entries
for the right module.

### On-device data

Each module keeps one JSON document in the app's document directory (`finance.json`,
`workout.json`, …). The store hydrates on first use, writes are debounced (250 ms) and every
document has a `parse` function that turns an old or damaged file into a valid document, so a
bad file never crashes a screen. See [ADR 0001](/docs/architecture/adr-0001-on-device-module-data).

Secrets (refresh token) go in SecureStore, never in the JSON documents.

## 4. API

`apps/nest-api` is a NestJS 11 modular monolith: controllers stay thin, services hold the logic,
repositories own Drizzle queries. Zod validates every request and the environment.

What the app uses today: email-code sign-in, refresh, logout, `GET /auth/me`, the profile and
avatar endpoints, and `GET`/`PUT /users/me/onboarding`. The contract lives in
[Backend API](/docs/backend-api).

Kept but not yet used by the app (decided in board card pos-8): password sign-in, magic links,
TOTP, passkeys and Google sign-in. Google and Apple sign-in on mobile is open as pos-12.

### Data model

| Table | Purpose |
| --- | --- |
| `users` | Identity: email, username, verification state, optional password hash |
| `user_profiles` | Display name, avatar URL, bio, time zone, locale |
| `sessions` | Refresh sessions: hashed token, expiry, user agent, IP, revocation |
| `auth_challenges` | Email codes and magic links, hashed, with attempt counts |
| `auth_identities` | Linked Google accounts |
| `totp_factors`, `passkeys`, `webauthn_challenges` | Second factors and passkeys |
| `onboarding_profiles` | The onboarding answers as JSON with a `schema_version`; the plan is derived on the device |

Schema changes are made in `src/database/schema` and committed with the generated migration;
migrations run on container start.

### Onboarding sync

The one piece of user data synced today. After sign-in the app compares its own timestamp with the
server's `updatedAt` and keeps whichever changed last, then uploads changes about a second after
they happen. A stored row from an older schema version reads as `null`, and the app uploads its
copy.

## 5. AI service

`apps/ai-api` (FastAPI, uv) exposes an assist endpoint behind a provider port, with an
OpenAI-compatible provider and a mock for tests. Nest calls it with `AI_SERVICE_TOKEN`; clients
never talk to it directly and never hold LLM keys. The app does not call `/ai/*` yet; the AI copy
in onboarding is generated on the device.

## 6. Security and known gaps

- Access tokens: JWT, 15 minutes. Refresh tokens: rotated, stored hashed; native clients receive
  them in the response body (`X-Client-Platform: native`) and keep them in SecureStore.
- Email codes are hashed, throttled (3 requests, 8 verifies per minute) and lock after repeated
  failures. Responses do not reveal whether an account exists.
- Helmet, CORS allowlist, CSRF checks for browser requests, rate limiting on auth routes.

Known gaps:

- **Avatars are written to the API container's disk** (`uploads/avatars`). On Render that disk is
  wiped on every deploy and restart. Move them to object storage (R2 or S3) before relying on them.
- **Module data has no backup.** Losing or resetting the phone loses expenses, meals and workouts.
- Rate limits are in memory, per instance.

## 7. Direction under discussion (not built)

These follow from the gaps above and are open for decision:

1. **On-device database.** Move module documents to SQLite (`expo-sqlite` + Drizzle, the same ORM
   as the API) so screens and insights can query across modules and writes stop rewriting whole
   files.
2. **One shared primitive under every module.** A small core of `actions` (what, when, whether it
   is part of the minimum day) and `entries` (done or skipped, value, date), with module-specific
   tables (expenses, meals, sessions) alongside. Streaks and "never miss twice" are then computed
   once for every module.
3. **Backup and multi-device sync.** Rows carry `updated_at` and soft-delete tombstones; the app
   pushes and pulls changes since its last sync. One person on a phone (and later a desktop app)
   does not need CRDTs; last write wins per row.
4. **AI with consent per module.** AI reads a compact daily digest of the modules the person has
   shared, only in the Insights tab, and proposes changes the person confirms.
5. **Reminders on the device.** Scheduled local notifications, so the most important nudges do not
   depend on the server.
