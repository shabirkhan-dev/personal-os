Personal OS is developed by independent backend, AI/Python, web, mobile, UI/UX, QA, reviewer, PM,
and documentation contributors. The
`.agents/` directory is the shared coordination layer for work that cannot be solved safely inside
one team's files.

## Current program: Personal OS Intelligence

The AI program is delivered as one vertical slice rather than a large parallel rewrite. The first
release is **Daily Intelligence + Personal OS Chat**, read-only and grounded in authorized Personal
OS data. The parent card is `2026-08-24-personal-os-intelligence.md`.

| Role | First responsibility | Boundary |
| --- | --- | --- |
| UI/UX | Design intelligence cards, chat command center, context references, action preview, and all states | `DESIGN.md` and approved shared tokens only |
| Backend | Own public AI gateway, context contracts, auth, authorization, rate limits, and API documentation | NestJS plus `backend-api.mdx` |
| AI/Python | Own structured insight/chat orchestration, provider adapter, output validation, evaluation, and cost/latency behavior | `apps/ai-api/**` |
| Web | Build responsive intelligence and chat surfaces from the documented contract | `apps/web/**` |
| Mobile | Build native intelligence and chat surfaces from the documented contract | `apps/mobile/**` |
| QA | Verify cross-client behavior, privacy, failure states, accessibility, and device/browser flows | Read-only; raises findings |
| Reviewer | Independently gate scope, contracts, security, evidence, and regression risk | Read-only; approves or requests changes |
| PM | Maintain sequence, dependencies, decisions, board cards, and release readiness | Board and product docs |

No client may call a model provider directly. No agent may implement confirmed mutations in the
first slice; action execution is a later parent-linked card with explicit confirmation and audit.

## The coordination map

| Location | Purpose | Ownership |
| --- | --- | --- |
| `.agents/board/open/` | New requests, bugs, and cross-team dependencies | Anyone can raise a card |
| `.agents/board/doing/` | Claimed work in progress | The named assignee |
| `.agents/board/done/` | Resolved work and decisions | The assignee closes the loop |
| `.agents/notes/backend.md` | Backend scratchpad | Backend team |
| `.agents/notes/frontend.md` | Web scratchpad | Web team |
| `.agents/notes/mobile.md` | Mobile scratchpad | Mobile team |
| `.agents/README.md` | Protocol and card lifecycle | Shared; change deliberately |

## Rules that prevent drift

1. Read `.agents/README.md` before raising or claiming a card.
2. Claim a card by moving it from `open/` to `doing/` and filling in `assignee`.
3. Do not edit another team's notes file. Raise a card instead.
4. Keep full API contracts in [Backend API](/docs/backend-api), not duplicated in cards or notes.
5. When an API changes, update the status board in the same commit and mark breaking changes clearly.
6. Stage explicit paths when committing; parallel contributors may have unrelated uncommitted work.

## A useful card

Keep cards short and actionable:

```md
From: mobile
To: backend
Priority: medium

What: Add a date-range completion endpoint for the weekly routine view.
Why: Today view only returns the current day.
Proposal: Return up to 90 days using the existing response envelope.
```

Link to the API status board instead of copying a contract into the card. A card is a hand-off, not
a second documentation system.
